# Attunetion backend parallel deployment

Production remains on Vercel. The AWS service is an IAM-protected Lambda Function URL for signed parity checks only. Native clients continue using the existing Vercel URL. Do not change native routing to the AWS URL: clients do not hold AWS credentials.

After the native and backend changes share a reviewed commit, run `npm run deploy:parallel` on an available owned computer with the existing Vercel session and `fishbowl-head` AWS profile. The command rejects tracked modifications and untracked backend source, builds an archive of the committed repository locally, copies the existing Vercel provider credential privately to SST's encrypted secret state, and deploys the same revision to both hosts. It does not push source. It refuses to run on or after 2026-10-22 07:00 UTC; recorded cutover state must be checked then.

AWS resources: one Node.js 24 Lambda (256 MB, 60-second timeout, the existing shared account concurrency limit10 (no dedicated reservation)), IAM authorization, one-week CloudWatch log retention, SST deployment state/assets and an encrypted SST provider secret. Capacity exception: a dedicated reservation2 was rejected because the applied account quota10 must retain at least10 unreserved executions; requesting12 was also rejected by Service Quotas, which requires a value greater than default1000. No larger quota increase was requested. Administrative IAM-only parity therefore uses the shared account cap10. Before public cutover, capacity isolation must be resolved. No provisioned concurrency, database, scheduler, worker, webhook or second public AI endpoint. Lambda execution needs only the log permissions generated by SST; the application contains no AWS SDK calls. There is no application IAM policy derived manually from source.

The AWS adapter serves all five AI routes used by the current native client, health, legal redirects and static public files. It intentionally omits the unused legacy `/api/intentions` in-memory CRUD routes; those are not a durable or authenticated user storage service and must not become a migration dependency.

Access and cost limits: Vercel's existing anonymous AI access is preserved when API_SECRET_KEY is absent. A configured API_SECRET_KEY is still enforced. Valid AI requests use a best-effort per-instance source-IP limit of 50 per two hours; source IP comes from Vercel's overwritten X-Forwarded-For or Lambda's request context. Instances and cold starts have separate limits. This is **not a global quota or provider spending cap**. Bodies are capped at 64 KiB with field and array bounds. Provider calls have a 45-second timeout and no automatic retries; output caps remain 512 tokens for individual operations, 4096/2048 for weekly generation. Existing weekly tiers reuse/shuffle prior results after 20 requests when sufficient history exists. AWS service use, log/state storage and OpenAI tokens can incur normal charges; no paid build compute is used. Before public AWS cutover, establish an appropriate public access and durable abuse/cost-control strategy and review native behavior.

The app does not log request bodies or provider error bodies. The limiter holds source IP and timestamps in process memory. The quota window is two hours; cleanup is opportunistic on later requests, so an idle warm instance may retain expired entries longer. Vercel retains hosting request/invocation metadata under its plan; AWS standard invocation logs retain request IDs, timing, duration and memory for one week. Do not equate this with no data collection. The canonical privacy policy is https://nathanfennel.com/attunetion/privacy.html.

Verification must record exact revision and URLs, unsigned AWS rejection, signed AWS health and AI request validation, Vercel health and validation, and one synthetic AI theme request and one weekly generation request per host (four total). No real personal intentions are used. A deployment or Git push alone is not proof of functional parity. Rollback: restore the prior recorded Vercel deployment using Vercel rollback and redeploy the corresponding committed AWS revision from an isolated checkout; preserve IAM protection and the single production owner. Actual rollback and repeat-deployment checks remain required before October readiness review.
